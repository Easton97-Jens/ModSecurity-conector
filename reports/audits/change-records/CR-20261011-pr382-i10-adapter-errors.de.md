### Technische Ursachen und Commitment

Common klassifiziert die erste Ursache gemäß bestehendem Contract. Die folgenden Default-HTTP-Status stammen aus `common/src/error.c`; der konkrete Adapter kann seinen bestehenden fail-closed Status verwenden. Keine universelle Hoststatus-Gleichheit wird behauptet.

| Canonical class | Common cause | Default HTTP status |
| --- | --- | --- |
| `INVALID_ENGINE_RESPONSE` | `MODSECURITY_FAILURE` | 500 |
| `CONNECTOR_ERROR` | `HOST_API_FAILURE`, `IO`, `INTERNAL` | 500 |
| `PROTOCOL_ERROR` | `PROTOCOL` | 502 |
| `ENGINE_TIMEOUT` | `TIMEOUT` | 504 |
| `ENGINE_UNAVAILABLE` | `RUNTIME_UNAVAILABLE` | 503 |

Die ausführbaren Matrizen variieren Vor-Commit, committed Headers, gestarteten Body und terminale Reentry. EOS-, Commit-, Host-ACK-, Native-/Body-/Companionfehler verwenden den realen erzeugten Fehler; Client Cancel/Upstream Disconnect werden nur an den vorhandenen jeweiligen produktiven Seams geprüft. Off/Safe wählen technische Fehlerbehandlung, niemals erfolgreichen Rule-log_only; echte späte Rule-log_only-Kontrollen bleiben erhalten. Eine Folgestörung bei Cleanup/Logging löscht die erste Ursache nicht.

## Implementierungsentscheidung und Begründung

Common-State-Machine und Wire-Protokolle bleiben erhalten. Produktive Caller verlangen exakt `1`, erhalten den ersten technischen Fehler und sperren weitere Callbacks. Vor Commit wird der vorhandene kanonische Fehlerstatus verwendet. Nach Commit propagieren Hostfehler/Stop-I/O und `http.ErrAbortHandler` bzw. nichtleere gRPC-Fehler den terminalen Zustand; es wird keine neue Response erfunden. Geprüfte Envoy-Cleanup-ABI ergänzt die kompatible bestehende ABI. Angeforderte HAProxy-Streamabschaltung wird nicht als beobachteter Clientabort aufgezeichnet.
