## Motivation and problem statement

The current master generator accepted a caller-selected `--out-dir` and used it
for directory creation and generated-file writes without containment. A
task-owned baseline control confirmed both an escaping parent traversal and an
existing final generated-header symlink could create or overwrite an external
file. This is a real filesystem-integrity boundary behind
`pythonsecurity:S8707`, not a cosmetic scanner signal.

The native libmodsecurity oracle also had an eight-argument `write_result`
helper and a `main` function above the configured cognitive-complexity limit.
The required maintenance work had to preserve the oracle's phase order, JSON
schema, exit states, null-safe serialization, and resource ownership. During
the refactor, the source-level body-append failure path was also changed from
two frees of the same non-null buffer to one-owner cleanup; an actual
libmodsecurity append-failure return was not reproduced, so this record does
not present that conditional path as a separately runtime-validated
vulnerability.

## Acceptance criteria

- `--out-dir` accepts only a relative path below the intentionally selected
  current working directory; absolute paths and every `..` component fail.
- Existing intermediate symlink escapes fail before a directory or generated
  file is created outside the output root.
- A pre-existing final generated-file symlink is replaced as a directory entry
  rather than followed; the external target remains absent.
- A valid nested output directory remains accepted and generated bytes remain
  unchanged for a representative HAProxy status set.
- `write_result` no longer exceeds the parameter-count threshold and request
  phase processing no longer resides in `main`, without changing CLI order,
  JSON fields/order, status classification, exit codes, or native phase order.
- No SonarQube Cloud rule, Quality Gate, exclusion, suppression, `NOSONAR`,
  Framework/MRTS source, Gitlink, workflow, or master change occurs.

## Implementation decision and rationale

`resolve_output_dir` now rejects absolute and parent-traversal input, resolves
the candidate under a strictly resolved current working directory, and confirms
canonical containment. `open_output_dir` creates and opens each directory
component with `O_DIRECTORY`, `O_NOFOLLOW`, and a directory descriptor. The
generator writes each fixed filename to an exclusive temporary file below that
opened directory and uses descriptor-anchored `os.replace` for the final name.
Platforms that lack the required descriptor primitives fail closed with a
normal CLI validation error.

The oracle groups request arguments and result fields in private contexts,
extracts the original linear phase sequence into `process_request`, and
centralizes cleanup in `cleanup_oracle`. `json_string` remains the sole
null-safe serializer for `whoami`; all error/success result fields and their
serialized order remain unchanged. The buffer is released immediately after a
successful append or once through the common cleanup owner on an error path.

## Alternatives considered

A lexical relative-path check alone was rejected because it cannot keep a
pre-existing final generated-file symlink from being followed. Canonical-path
containment without descriptor-anchored creation was also rejected because a
directory entry can be replaced after canonicalization and before a path-based
write. The selected design combines input rejection, canonical containment,
no-follow directory-descriptor traversal, and atomic final replacement; it
fails closed where those primitives are unavailable.

## Security impact

The baseline S8707 source-to-sink path is directly demonstrated in task-owned
temporary storage: a relative traversal and a final generated-file symlink
could direct a fixed generated header outside the selected output root. The
candidate adds lexical, canonical, and descriptor-anchored controls before the
write sinks, then atomically replaces the final directory entry rather than
writing through it.

The resulting guarantee assumes that the caller chooses a trusted, exclusive
current-working-directory root. A party able to rename that root's ancestry or
modify the opened output directory concurrently is outside this CLI boundary;
the implementation does not claim a global hostile-shared-directory guarantee.
The local security review found no diff-introduced candidate under that
explicit assumption. No SonarQube Cloud issue is closed until an exact delivery
head has an observed hosted analysis.

## Compatibility and generated artifacts

For the representative `501,403` input, generated header, C source, and
HAProxy configuration bytes are compatible with the base generator. The
output-file replacement mechanism intentionally changes filesystem metadata
semantics: replacement creates a new file subject to the process umask and
breaks an existing hardlink rather than truncating its referent. No generated
artifact is committed by this change.

## Known limitations

The generator deliberately changes output-file replacement metadata semantics:
atomic replacement uses a new file subject to the process umask and breaks an
existing hardlink rather than truncating its referent. No direct production
caller was found in the repository beyond the focused smoke checker. The
native append-failure branch could not be forced with the available rule/body
control, so the common-cleanup correction is source-evidenced but not claimed
as a reproduced memory-safety event.

## Remaining risks

The output root must remain exclusive while a caller runs the generator. A
privileged concurrent writer with authority over its ancestry or opened
directory could affect later namespace observations, even though the generator
does not follow an existing intermediate or final symlink. The broader Sonar
backlog and all other components are outside this focused `ci/tools` task.

## Checks not run and rationale
